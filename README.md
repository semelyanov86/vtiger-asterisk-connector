# Vtiger Asterisk Connector

Go-сервис и набор воспроизводимых эксплуатационных настроек для интеграции
Asterisk с Vtiger CRM. Проект охватывает не только коннектор, но и установку,
настройку, защиту, резервное копирование и приёмочное тестирование телефонии на
целевом сервере.

## Статус проекта

Проект находится на начальном этапе. `main.go` пока является заглушкой, а
архитектура коннектора, способ интеграции с Asterisk и подход к dependency
injection ещё не утверждены. Java-код в `legacy/` нужен для изучения прежнего
поведения, но не является основой новой реализации.

- Язык: Go 1.26.
- CRM: Vtiger 8.4.0 с модулем `PBXManager`.
- Целевой сервер: `cm.gus-global.com`.
- Минимальное покрытие: 80%, источник истины —
  `.coverage-thresholds.json`.
- CI: форматирование, `go vet`, `golangci-lint`, сборка, тесты с race detector
  и порог покрытия.

## Источники требований

Используйте источники в следующем порядке:

1. Явно согласованные решения и техническое задание в
   [`documentatnion/tz.odt`](documentatnion/tz.odt).
2. Фактические контракты установленного Vtiger и выбранной актуальной версии
   Asterisk.
3. Официальная документация поддерживаемых версий Asterisk и Vtiger.
4. `legacy/asteriskconnector-master` — только как описание прежнего поведения.

Каталог `documentatnion/` уже создан в репозитории именно с таким именем
(с опечаткой). В текущем рабочем окружении исходники CRM обнаружены в
`/data/gus/vtigercrm`, хотя исходно был указан путь `/data/gus/vtiger`. Перед
изменениями в CRM всегда проверяйте актуальный путь. На целевом сервере CRM
развёрнута в `/var/www/vtiger/vtigercrm`.

## Быстрый старт

Требуются Go 1.26, Task 3 и `golangci-lint` версии, совместимой с
`.golangci.yml`.

```bash
go mod tidy
go build ./...
go test ./...
go test -race -shuffle=on ./...
go vet ./...
golangci-lint run ./...
bash bin/coverage-check.sh
```

Подключение к серверу:

```bash
task ssh
```

Команда открывает интерактивный SSH-сеанс `root@cm.gus-global.com`. Само
подключение не означает разрешение изменять сервер: сначала снимите состояние,
согласуйте изменение и подготовьте способ отката.

## Функциональные требования

### Телефония

- установка и настройка актуальной поддерживаемой версии Asterisk/FreePBX;
- SIP-транк и корпоративный номер;
- добавочные номера 100–103 и работа SIP-клиентов вне офиса;
- немецкое приветствие и уведомление о записи;
- IVR: ввод добавочного, `4` для факса, `5` или ожидание для оператора;
- одновременный вызов сотрудников, резервная переадресация владельцу и
  голосовая почта;
- запись всех входящих и исходящих разговоров;
- хранение записей на VPS 90 дней и автоматическое удаление;
- резервное копирование;
- приём факса, преобразование в PDF и отправка по email.

### Интеграция с Vtiger

- определение клиента по номеру и всплывающая карточка при входящем звонке;
- предложение создать лид для неизвестного номера;
- история звонков, направление, статусы, время, длительность и ответивший
  сотрудник;
- безопасная ссылка на запись разговора;
- Click-to-Call из CRM с корпоративным Caller ID;
- задача «Перезвонить» после голосового сообщения;
- корректная обработка повторных, запоздавших и пришедших не по порядку
  событий.

Базовый поток вызова из ТЗ:

```text
SIP-провайдер
    |
    v
Asterisk / FreePBX -> приветствие и IVR
    |                         |
    |                         +-> факс -> PDF -> email
    v
101 + 102 + 103 (15 секунд)
    |
    v
100 + мобильный владельца (20 секунд)
    |
    v
голосовая почта -> email + задача в Vtiger

Asterisk <-> Go-коннектор <-> Vtiger PBXManager
                  |
                  +-> метаданные и ссылки на записи
```

В ТЗ есть несогласованность: сценарий маршрутизации сначала вызывает 101–103,
а затем 100 и мобильный владельца, но приёмочный чек-лист требует одновременный
вызов всех четырёх добавочных. Это необходимо согласовать до реализации
dialplan и приёмочных тестов.

## Актуальный контракт Vtiger

По состоянию на 19 августа 2026 года установленный Vtiger 8.4.0 сохраняет
следующий контракт `PBXManager`:

- входящий callback:
  `/modules/PBXManager/callbacks/PBXManager.php`;
- аутентификация callback-параметром `vtigersignature`;
- состояния обработки: `StartApp`, `DialAnswer`, `Record`, `EndCall`, `Hangup`;
- Click-to-Call обращается к настроенному URL коннектора `/makecall`;
- настройки CRM включают URL коннектора, outbound context, trunk и общий
  секрет.

Это описание зафиксировано для ориентира, а не для слепого копирования.
Перед реализацией требуется определить и протестировать новый версионируемый
контракт, способ аутентификации, таймауты, повторные запросы и идемпотентность.
Секреты нельзя передавать в URL, писать в логи или хранить в репозитории.

## Что делает legacy-коннектор

`legacy/asteriskconnector-master` содержит две Java-части:

- `vtigeragi`: FastAGI-обработчик, AMI listener, запуск Dial/Monitor и отправка
  событий в webapp;
- `vtigerwebapp`: встроенный Jetty, SQLite для корреляции событий, HTTP
  callback в Vtiger, `/makecall` для AMI Originate и `/recording` для выдачи
  WAV-файла.

Легаси оперирует событиями AGI, Bridge, CDR, Hangup, Dial и Record, общим
секретом и XML-ответами Vtiger. Его FastAGI-порт 4573, устаревшие SIP-команды,
схема событий, параметры HTTP, модель хранения, таймауты и защита endpoint'ов
не считаются требованиями нового сервиса.

## Целевые инженерные свойства

- долгоживущий процесс с graceful shutdown и явными lifecycle/health checks;
- конфигурация через окружение или защищённые файлы, без секретов в Git;
- структурированные логи без телефонов, токенов и других персональных данных;
- ограниченные таймауты, backoff с jitter и восстановление соединения;
- идемпотентная обработка событий и устойчивость к reconnect/replay;
- минимальные привилегии для Asterisk/AMI, CRM и файлов записей;
- воспроизводимая настройка сервера вместо недокументированных ручных команд;
- unit-, integration- и contract-тесты; интеграционные тесты отделяются build
  tag `integration` и не используют production-системы по умолчанию.

## Состояние целевого сервера

Read-only инвентаризация выполнена 19 августа 2026 года:

| Параметр | Значение |
| --- | --- |
| ОС | Ubuntu 24.04.4 LTS, Linux 6.8, x86-64, KVM |
| Ресурсы | 6 vCPU, 17 GiB RAM, swap отсутствует |
| Диск | около 1 TB ext4, занято около 11 GB |
| Время | `Europe/Berlin`, NTP синхронизирован |
| Web/DB | nginx 1.28.3, Apache 2.4.58, PHP 8.4.21, MySQL 8.0.46 |
| CRM | Vtiger 8.4.0 в `/var/www/vtiger/vtigercrm` |
| Контейнеры | Docker 29.7.2; запущен OpenCloud |
| Asterisk/FreePBX | не установлены, сервис и телефонические порты отсутствуют |
| Защита хоста | UFW и fail2ban не активны; внешний firewall не проверялся |

Перед установкой телефонии необходимо отдельно спроектировать сетевую модель,
firewall, TLS/SRTP, защиту SIP от перебора, least-privilege доступ к AMI/API,
ротацию и шифрование записей, мониторинг, backup/restore и rollback. Не
открывайте SIP/AMI/HTTP-порты до согласования этой модели.

## Открытые решения

До разработки основной функциональности нужно согласовать:

- архитектуру сервиса и способ dependency injection;
- поддерживаемую версию Asterisk и границы использования AMI, ARI и AGI;
- FreePBX или полностью управляемую конфигурацию Asterisk;
- формат и версионирование контракта с Vtiger;
- модель хранения состояния, дедупликации и корреляции звонков;
- авторизацию и срок жизни ссылок на записи;
- правила удаления записей через 90 дней с учётом backup;
- точный сценарий звонка для добавочного 100;
- SIP-провайдера, номер, trunk, сертификаты и сетевые ограничения.

## Разработка и CI

Следуйте [`AGENTS.md`](AGENTS.md). Разработка ведётся через TDD: тест должен
сначала зафиксировать ожидаемое поведение и упасть, затем добавляется минимальная
реализация. Табличные тесты используют именованные subtests; независимые тесты
по возможности запускаются параллельно. Код с goroutine проверяется race
detector и тестами на утечки.

`golangci-lint` настраивается только через `.golangci.yml`. Любой `//nolint`
должен указывать конкретный linter и объяснение. Перед merge обязательны все
локально доступные проверки, совпадающие с CI.
